# KFC 仕様地図 — 索引

**Kohaku Find/Change（KFC）が「今どう振る舞うか」を、規則を1文ずつ並べた地図。**
コードの地図（`docs/ai-notes/kbs-file-map.md`＝SDK フォルダー側・この repo の外）とは別物で、
あちらが「どのファイルが何か」、こちらが「製品として何がどう決まっているか」を持つ。
形は KCM の仕様地図（`source/sdksamples/KCM/docs/spec-map/`）と同じ。

---

## この地図の目的

作者（＝あなた）が読んで、**頭の中の仕様と実装が食い違っているところを見つけるため**。
見つけたら、その場で書き込む。書き込まれたものは実装の変更依頼として扱われる。

---

## 訂正の書き方

各項目には空の `訂正:` 欄が付いている。そこに書く。

```markdown
- **GEN-20** 検索できるタブは4つで、オブジェクトとカラーのタブでは Find in … が灰色になる。
  - 訂正: オブジェクトのタブは将来やるかもしれないので「今は」と書いておいて
```

- **書く場所は訂正欄でなくてもよい。** 規則の文そのものを直しても、項目ごと消しても、
  新しい項目を足しても構わない。**このフォルダーは git 管理下にあるので、どう変えても検出できる。**
- ID（`GEN-20` など）は**やり取りのための番号**。これで指せば話が早い。番号は詰め直さない。
- 途中に項目を足すときは**枝番**（`GEN-20b`）を使い、既存の番号は動かさない。
- ★**書き方は気にしなくてよい。走り書きで構わない。**
  **それを規則文として整った日本語にするのは私（Claude）の仕事**（KCM の地図と同じお約束）。
  訂正が反映されると、訂正欄には `✅<日付> 対応` と、どこへ反映したかだけが残る。
- ★**ID の接頭辞は KCM の地図と重ならないものにしてある**（KCM の `RUN-` `ST-` `BK-` などと、KFC の `GEN-` `FIND-` `SCOPE-` などを取り違えないため）。

---

## ★印の意味

**★が付いた項目 = 過去に「意図的にこう決めた」と記録が残っているもの。**

そこに訂正が入った場合は、決定を覆すことになるので、**実装する前に必ず確認を取る**。
「なぜそう決めたか」を添えて聞くので、その上で判断できる。

## 私（Claude）が次のセッションでやること

**この地図を開いたら、まず訂正を拾う。**

```
cd source/sdksamples/KFC
git diff -- docs/spec-map/          # 未コミットの書き込み
git log -p -- docs/spec-map/        # コミット済みの書き込み
```

（フォルダー名 `KFC` は、KFC への改名の後は `KFC` になる。）

拾った訂正は、**手を動かす前に分類する**。分類は実コードを読んで決める。
訂正を額面通りに受けてコードを触らない。

| 種別 | 中身 | すること |
|---|---|---|
| **A** | 地図が実装を読み違えていた | **地図を直す**（コードは触らない） |
| **B** | 地図は実装と合っており、実装のほうが意図と違う | **コードを直す** |
| **C** | ★印の項目への訂正（過去の決定を覆す） | **先に理由を添えて確認**を取る |
| **Q** | 「こうしてほしい」ではなく**質問** | **実装を読んで答える。** 答えた結果が A/B/C のどれかなら、そのまま手を当てる |
| **F** | **今は無い機能が欲しい**（要望） | 地図に `⬜未実装の要望` として枝番で残し、**実装は別途提案してから**。地図は「今の実装」を写すものなので、要望を規則文に混ぜない |

★★**訂正欄には質問を書いてよい。**「これはこうなっているのでは？」で構わない ―― 答えを探すのは私の仕事。
（KCM の地図では、質問1つが地図の不正確をあぶり出した。**質問は指摘と同じだけ役に立つ。**）

対応が済んだら、**規則文を新しい実装に合わせて書き換え、訂正欄に `✅<日付> 対応` を残す。**
この地図は常に「今の実装」を表す ―― それが崩れると、次の走査で同じ訂正をもう一度拾ってしまう。

## 作り方の約束

- **憶測で書かない。** 実装（`.h` の契約・`.fr` の宣言・`.cpp` の分岐）を読んで確認したものだけを規則にする。
  memory や過去のノートは入口としてしか使わず、必ずコードで裏を取る。
- **読み切れなかった点は消さずに残す。** 各章の末尾に `⬜ この章で未確認` として並べる。
  空欄を「そんな決まりは無い」と読ませないため。
- 章の冒頭に、その章がコード地図のどのブロックにあたるかを1行入れる。
- 画面に出る英語の文言（メニュー名・メッセージ欄の文）は、**コードにある綴りのまま**写す。
